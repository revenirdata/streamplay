# MQTT fleet simulation

StreamPlay can drive a bounded fleet of software devices against one to four isolated MQTT targets. Every logical event has a stable ID and identical payload across targets, so a current path and a candidate path can be compared without physical hardware.

```text
simulated devices ─┬─> current candidate broker ─> isolated downstream sink
                   └─> new candidate broker ─────> isolated downstream sink
                         │
                         └─ acknowledgement ledger + latency summary
```

The simulator measures MQTT publish acknowledgement. That proves what each broker accepted at the protocol boundary; it does not prove Kinesis persistence or downstream processing. Candidate integrations must add independent Kinesis and output receipts keyed by the same `event_id`.

## Run a local profile

Start an isolated MQTT broker, then run:

```bash
npm run simulate -- examples/simulations/mqtt-fleet.local.json
```

The command writes an NDJSON receipt ledger and a JSON summary under `.streamplay/simulations/`. The example uses 25 devices. Increase `devices.count` only after verifying the machine and broker can sustain the connection and message rate.

Remote targets are rejected unless the operator passes `--allow-remote`. Hostnames that look like production are still rejected; this load generator is for isolated endpoints.

To compare two targets, add a second entry to `targets`. Secrets do not belong in the profile. Use `urlEnv`, `usernameEnv`, and `passwordEnv` to name environment variables. A broker that derives a per-device password with HMAC-SHA256 can use `hmacSecretEnv`, `usernameTemplate`, and `clientIdTemplate`; the secret stays in the named environment variable. TLS targets may use `caFile`, `certFile`, `keyFile`, `serverName`, and `alpn`.

## Traffic and failure controls

- `messagesPerDevice`, `intervalMs`, `jitterMs`, and `rampUpMs` control steady-state traffic and connection ramp.
- `targetPayloadBytes` adds an inert padding field when needed so generated payloads meet a requested minimum size. The acknowledgement summary records accepted bytes.
- `duplicateEvery` republishes the same event ID and payload. It tests downstream idempotency rather than inventing a new event.
- `reconnectEveryDevice`, `reconnectAfterMessage`, and `reconnectDelayMs` exercise disconnect and reconnect behavior for a deterministic device subset.
- `connectConcurrency` bounds the initial connection storm generated by the client machine.
- `counter` produces a deterministic monotonic value for payload templates that use `{{counter}}`; `{{uptime}}` advances with the message sequence.

Profiles are capped at 10,000 devices, 5,000,000 logical events, and four targets. Those are safety bounds, not a claim that one laptop can accurately reproduce production capacity. A production-scale result should run on dedicated load generators in the same network region as isolated candidate infrastructure.

## Staged architecture validation

1. **Local correctness:** use small deterministic profiles against local brokers and assert exact event IDs.
2. **Candidate bake-off:** run a production-shaped profile against isolated EMQX and/or AWS IoT Core endpoints, with no customer commands or notifications.
3. **Shadow comparison:** duplicate real accepted telemetry to isolated current/candidate sinks. The current path alone remains authoritative.
4. **Canary routing:** route an explicit device cohort to the candidate path after shadow reconciliation passes.
5. **Gradual cutover:** expand through predeclared stages with error, loss, latency, backlog recovery, and rollback gates.

Do not aim this tool at production endpoints by default. Profiles and output ledgers may contain payloads and identifiers; keep private fixtures outside this public repository.
